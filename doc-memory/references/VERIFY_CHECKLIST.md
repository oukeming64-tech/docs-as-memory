# VERIFY_CHECKLIST — 对照实现核正文档（Verify / Patch）

这份清单内置在 `doc-memory` 中，不依赖其他技能。目标不是“把文档写得更满”，
而是确认准备修改的每句话都有当前实现依据。

## 输入

- R 阶段 `affected` 命中的碎片；
- 当前工作树的实际 diff；
- 与改动相关的实现、配置、公共 API、schema、测试和夹具。

## 核对顺序

1. 先读 diff，列出被改变的行为、接口、配置、数据或工作流。
2. 只打开能证明这些变化的最小实现与测试集合。
3. 用 `affected` 结果与 diff 推导范围取并集；不要顺手扩散到无关 README。
4. 逐条标记文档事实为：
   - `confirmed`：当前实现或测试直接支持；
   - `stale`：与当前事实冲突，需要修改；
   - `unknown`：证据不足，不能猜；
   - `decision-needed`：涉及产品、规范、安全策略或架构取舍，需用户裁决。
5. 搜索范围内与现实冲突的状态词和旧标识，例如
   `todo / pending / not done / next / blocked / 旧版本号`。

## 证据优先级

通常按以下顺序判断：

`当前实现与可执行结果 > 公共 API / 配置 / schema > 测试与夹具 > 当前文档 > 作者摘要`

规范、安全策略、产品契约和架构决策不是普通事实漂移。它们与实现冲突时，报告
冲突和最小建议，等待用户决定，不要静默把规范改成现状。

## Patch 纪律

- 只改 `stale` 且在锁定范围内的内容；
- 不把计划、候选或未来工作写成已经交付；
- 有 frontmatter 时，只有完成事实核对才更新 `verified_at`；
- 交付说明明确写出：改了什么、没改什么、仍待什么决定。

## 停止条件

出现以下任一情况时阻断完成声称：

- 不知道哪份规范是权威来源；
- 证据不足却需要补写事实；
- 文档仍把已交付内容写成未来，或反过来；
- 修改需要用户未作出的产品、安全或架构决定。
